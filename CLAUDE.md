# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Saga is a VS Code extension that turns product briefs and technical designs into INVEST-compliant agile stories (with Gherkin acceptance criteria), pushes them to Jira Cloud or Azure DevOps, and keeps both sides in sync — all version-controlled in a `.saga/` folder inside the workspace. It also generates agent prompts and `AGENTS.md` for coding agents. See [docs/saga-prd.md](docs/saga-prd.md) for the full PRD.

**Post-M5.6 fixes — ADO tracker gaps:**
- **`AdoAdapter.testConnection()` 404 fix:** was requesting `/{project}/_apis/project?api-version=...` (singular `project`, project name used as an org-level path prefix). Azure DevOps's real Get Project endpoint is `{orgUrl}/_apis/projects/{projectId}?api-version=...` — plural collection, project as the final resource segment, no prefix. Fixed in `src/tracker/ado.ts`. The `project`-as-path-prefix shape is only correct for the work-item-creation endpoint (`{org}/{project}/_apis/wit/workitems/$type`, used by `createWorkItem`) — `testConnection()` had copied that shape onto the wrong endpoint. This was an isolated bug; all other ADO REST calls (fetch/update/delete work item) were already correct.
- **ADO parity gap — subtask type, AC field, story points field:** ADO previously had no config equivalent to Jira's `subtask_issue_type` / `ac_field_id` / `story_points_field_id`. AC and story points were already pushed to ADO, but via hardcoded field refs (`Microsoft.VSTS.Common.AcceptanceCriteria`, `Microsoft.VSTS.Scheduling.StoryPoints`); subtask push was already implemented but hardcoded to work item type `'Task'`. None of these were exposed as config, so users on custom process templates had no way to override them, and the Settings UI's ADO "Advanced field settings" section only had 2 fields (epic/story work item type) vs. Jira's 5. Added `ado.subtask_work_item_type` (default `'Task'`), `ado.ac_field_id` (default `'Microsoft.VSTS.Common.AcceptanceCriteria'`), `ado.story_points_field_id` (optional, falls back to the standard field) to the schema — mirroring Jira's pattern exactly, including the same "omit from `config.yaml` when empty" convention for `story_points_field_id`. Wired through `AdoConfig` (`field-mapping.ts`), `AdoAdapter.pushSubtask` (`ado.ts`), both `AdoAdapter` construction sites (`factory.ts` and `settings-panel.ts`'s `testTrackerConnection`), and a new 3-field addition to the Settings Webview's ADO advanced section (`SettingsEditor.tsx`).
- **ADO 400 errors were undiagnosable + one bad story aborted a whole batch:** `AdoAdapter.assertOk()` (`src/tracker/ado.ts`) threw `"ADO {method} {path} failed: {status} {statusText}"` with no detail from the response body, even though it already fetched the body — so a 400 caused by an invalid field reference (e.g. `ac_field_id`/`story_points_field_id` not present on the target work item type's layout for a given process template) surfaced as a bare, undiagnosable "400 Bad Request" with no indication of which field was the problem. Fixed: `assertOk()` now parses the ADO JSON error body for its `message` field (falling back to raw body text if not JSON) and appends it to the thrown message. Separately, the F15c "push N stories" flow in `saga.pushEpic` (`src/extension.ts`) looped over unpushed stories calling `pushOneStory()` with no per-item try/catch, so one story hitting a 400 aborted the whole loop and surfaced as a generic `"Error running command saga.pushEpic"` — misleading since the epic push itself had already succeeded by that point. Now matches `saga.pushAll`'s existing per-item resilience pattern: failures are caught individually, logged to the Saga Output Channel, and a final summary (`"Pushed X/Y stories... Z failed"` with a "Show Output" action) is shown instead of one story's failure hiding the others' success.
- **ADO story/subtask → parent link used a relative URL, causing "Linking to a work item requires the full url" (400):** `toAdoStoryPatch`/`toAdoSubtaskPatch` in `src/tracker/field-mapping.ts` built the `System.LinkTypes.Hierarchy-Reverse` relation as `url: `_apis/wit/workItems/${id}`` — a relative path. ADO's work item relations API requires the full absolute URL (`{orgUrl}/_apis/wit/workItems/{id}`), and rejects a relative one with exactly this 400 message (only surfaced correctly after the `assertOk()` fix above). Both functions now take `orgUrl: string` as a new parameter (passed from `AdoAdapter.pushStory`/`pushSubtask` via `this.orgUrl`) and build the relation URL as `${orgUrl}/_apis/wit/workItems/${id}`. `orgUrl` is connection info, not process-template config, so it's threaded as a separate parameter rather than added to `AdoConfig`.
- **"Push N Stories" (F15c, from `saga.pushEpic`) never offered to push subtasks:** by design (see the "Subtask tracker push" constraint below), subtask push has always been a separate, explicit, opt-in action — but it was only ever surfaced via `saga.pushStory`'s own success notification, not via the epic's bulk "Push N Stories" follow-up, because that flow calls the subtask-agnostic `pushOneStory()` helper directly rather than going through `saga.pushStory`'s command handler. Users who pushed an epic and then bulk-pushed its stories had no way to discover that subtasks still needed a separate action. Fixed by extending (not replacing) the same opt-in pattern: after "Push N Stories" completes, `saga.pushEpic` now collects every unpushed subtask across the just-pushed stories and — only if any exist — shows its own "Push N Subtasks" notification, reusing `pushOneSubtask()` with the same per-item try/catch + Output Channel logging as the story loop. `saga.pushAll` is deliberately left unchanged (still excludes subtasks entirely) — that scope boundary was an explicit product decision, not the gap being fixed here.
- **Sync always showed "remote-only"/pull, even with zero real remote changes, and even overwrote real local edits:** `buildSyncPlan()`'s 3-way hash comparison in `sync-engine.ts` was correctly implemented, but `hashRemoteEpic()`/`hashRemoteStory()` were computed on text that `fetchEpic()`/`fetchStory()` reconstructed *lossily* relative to what was originally pushed — so the remote hash almost never matched the base/local hash even with no actual edits, and every item fell into the `remote-only` branch (never `in-sync`, and never `conflict` — which is why "Keep Local" was never even offered as a choice, since the UI has no local-vs-base divergence to react to). Two independent root causes, one per provider, both fixed:
  - **Jira**: `toAdf()` (`field-mapping.ts`) splits a multi-paragraph description into separate ADF paragraph nodes on push; `extractText()` (`jira.ts`) reconstructed them joined by a single `\n` instead of a blank line (`\n\n`) on fetch, permanently losing the paragraph break. Since every story description is built as `"As a X\nI want Y\nSo that Z\n\n<description>"` (itself blank-line-separated), **every story with a non-empty `description` field hit this**, not just edge cases. Fixed: `extractText()` now joins block-level nodes with `\n\n`, matching `toAdf()`'s input shape exactly. `adfToText()`'s outer `.trim()` still strips the harmless trailing blank line for single-paragraph text, so this is a strict fix with no regression for the simple case.
  - **ADO**: `htmlToText()` (`ado.ts`) collapsed *all* whitespace (`\s+` → `' '`), destroying every newline in a pushed description — ADO's `System.Description` field is sent raw text with literal `\n` on push (`toAdoEpicPatch`/`toAdoStoryPatch` in `field-mapping.ts`), so any multi-line epic or story description was guaranteed to mismatch on the next fetch. Fixed: `htmlToText()` now converts `</p>`/`</div>`/`<br>` boundaries to newlines *before* stripping tags, and only collapses horizontal whitespace (spaces/tabs), preserving line structure both for literal `\n` already in the text and for HTML block boundaries.
  - Both fixes are narrowly scoped to the text-reconstruction helpers (`extractText`/`htmlToText`) — the downstream regex-based parsers (`parseUserStoryText`, `extractAcFromDescription`, `parseAdoUserStoryHtml`, `parseAdoAcHtml`) already used whitespace-flexible (`\s*`/`\s+`) matching and needed no changes; they absorb the corrected spacing without any behavior change for well-formed content.
- **Sync STILL always showed "remote-only" after the text-formatting fix above — two deeper, deterministic bugs, affecting every story regardless of content:** the text round-trip fix was real but insufficient; a full push → sync → accept-pull → sync-again cycle still showed false mismatches on every story. Root-caused to two structural bugs in the hash comparison itself, not the text formatting:
  - **Structurally mismatched hash shapes (the main bug):** `hashStory()` includes an 11th canonical field, `subtasks` (see the M5.1 "Subtask hash inclusion" constraint's original intent — this is legitimate for local-only drift, so it can't just be deleted), but `hashRemoteStory()` has no `subtasks` field at all (correctly — trackers have no story-level subtask concept; subtasks are their own independently-synced tracker items per M5.1). `pushStory()` in both `jira.ts` and `ado.ts`, and every `local_hash`/`last_synced_hash` write site in `extension.ts` and `sync-review-panel.ts`, were calling `hashStory()` — the 11-key version — to compute the stored sync baseline. Since `JSON.stringify` output (and therefore the SHA-256) differs whenever the key set differs, **`hashRemoteStory()` could never equal a baseline computed from `hashStory()` for ANY story, ever, regardless of content** — a mathematical certainty, not a probabilistic one, which is why the bug survived the text-formatting fix and did not self-heal after a pull re-baseline. Fixed: added `hashComparableStory()` to `hash.ts` — the same field set as `hashRemoteStory()` (10 keys, no `subtasks`) — and switched every push/pull `local_hash`/`last_synced_hash`/sync-store write site to use it instead of `hashStory()`. `storyEffectiveStatus()` in `src/tree/saga-tree.ts` (the tree's `[drifted ●]` badge) was updated to match — it now compares `hashComparableStory(story)` against `remote.last_synced_hash`, plus a **separate** per-subtask check (`hashComparableSubtask(sub) !== sub.remote.last_synced_hash` for each subtask with a remote key) so that editing a subtask still correctly marks the parent story drifted, without reintroducing the same structural mismatch in reverse. `hashStory()` itself is unchanged and still exported, but is no longer used anywhere in the tracker push/pull/sync path — see its updated docstring.
  - **Pull-path fallback values baked into the stored baseline:** `SyncReviewPanel.runApply()`'s pull/take-remote branch merges `remote.x || local.x` (falling back to local when the tracker's round-tripped text parses to an empty string) into the `Story`/`Epic` object it writes to disk — reasonable, since we never want to null out real content. But it was then hashing that **merged, fallback-containing** object (`hashStory(parsed)`/`hashEpic(parsedEpic)`) and storing the result as `last_synced_hash` — while `hashRemoteStory()`/`hashRemoteEpic()` on the *next* sync pass always hashes the *raw, un-fallback'd* `remote` values. Whenever a fallback was actually applied, the stored baseline could never again match what the next fetch produces, permanently. Fixed: the stored `remote.last_synced_hash` and sync-store `last_synced_hash` are now computed directly via `hashRemoteStory(remote, ...)`/`hashRemoteEpic(remote, ...)` — exactly what the next classification pass will recompute — while `local_hash` still uses `hashComparableStory(parsed)`/`hashEpic(parsedEpic)` on the actually-written (possibly fallback-containing) content. It's correct and expected for these two to differ by exactly one "local-only" drift flag immediately after a pull that used a fallback — that's the honest state (the written content doesn't perfectly represent the tracker), not a bug, and it resolves itself on the next push.
- **After the two fixes above, sync stopped pushing local edits — a hash-scheme migration gap, not a new bug:** `classifyEpic`/`classifyStory` in `sync-engine.ts` computed `localHash` as `local.local_hash ?? hashEpic(local)` / `local.local_hash ?? hashComparableStory(local)` — i.e. they trusted the **stored** `local_hash` from disk when present, only falling back to a fresh computation when absent. For any epic/story pushed *before* the two fixes above, the on-disk `local_hash` and `remote.last_synced_hash` were still whatever the *old* hash function produced (the mismatched-field-set `hashStory()`, or the pre-format-fix `hashRemoteEpic`/`hashRemoteStory` inputs) — nothing had re-pushed them yet to refresh those stored values. Since both `local.local_hash` (stale, trusted) and `baseHash` (also stale, from the same original push) were the *same* old value, `localChanged` came back `false` — masking real local edits made in the meantime, because the comparison never re-derived the local hash from current content. Meanwhile `remoteHash` (freshly computed with the corrected function) diverged from that stale `baseHash` for unrelated reasons (different hash scheme, not a real remote change), classifying as `remote-only` — whose default resolution is `pull`, silently discarding the real local edit that never got a chance to classify as changed. **Fixed:** `classifyEpic`/`classifyStory` now always call `hashEpic(local)`/`hashComparableStory(local)` fresh, never trusting a stored `local_hash` — cheap, since it's just hashing an in-memory object, and it makes any stale on-disk hash from a since-changed hash function irrelevant to classification (this already matched `classifySubtask`'s existing behavior, which never trusted a stored subtask hash to begin with — the bug was specific to the epic/story functions). The `baseHash` (from `last_synced_hash`) is still read from storage, since it represents "what the tracker had at last sync" and can't be recomputed from current state — but for pre-fix items it's now correctly detected as unreliable (both `localChanged` and `remoteChanged` come back `true` against the stale baseline), which classifies as `conflict` rather than `remote-only`. `conflict`'s default resolution is `keep-local` (push wins, never silently discards local content) — so the very first sync per pre-existing item after this fix safely re-baselines by pushing local content forward, and every subsequent sync correctly shows `in-sync` once both hash sides are written with the consistent, corrected functions.
- **Full re-audit (post above 5 fixes) — one more instance of the same bug class, in the subtask pull path:** a fresh, skeptical audit of the entire hash/classification pipeline (epics, stories, AND subtasks — subtasks hadn't been re-verified since the earlier fixes) confirmed everything else holds: `classifySubtask` already always recomputed fresh (never had the stale-trust bug); every epic/story/subtask push-path write site uses matched, field-set-compatible hash pairs; the epic and story pull paths correctly hash raw `remote` for the baseline. The one survivor: `SyncReviewPanel.runApply()`'s **subtask** pull/take-remote branch (`sync-review-panel.ts`) computed `last_synced_hash` from `hashComparableSubtask({ id, title: remote.title || local.title, done })` — the fallback-substituted title — instead of `hashRemoteSubtask(remote, local.id)` on the raw `remote` object, the same class of bug already fixed for stories/epics (fix #4 above). This only manifests when a tracker returns an empty/falsy title for a subtask (fetch parsing edge case), but when it does, that one subtask would show spurious drift/conflict on every subsequent sync forever. **Fixed** to match the story/epic pattern exactly: `last_synced_hash` is now `hashRemoteSubtask(remote, local.id)`, computed once and reused for both the subtask's `remote` field and the sync-store mapping; the written `title` field still applies the local fallback for display purposes, decoupled from what gets hashed as the baseline.

## Architecture

### Entry point
`src/extension.ts` exports `async activate(context)` and `deactivate()`. All commands, tree views, and Webview panels are registered here via `context.subscriptions`. Module-level helpers: `getSagaChannel()`, `logTokenUsage()`, `isAbortError()`.

### Module structure

Two core interfaces carry extensibility:

- **`LLMProvider`** (`src/llm/provider.ts`) — provider-agnostic AI access. Adapters: `VsCodeLmProvider` (Copilot), `LocalLmProvider` (Ollama/LM Studio), `AnthropicProvider`, `GeminiProvider`, `OpenAIByokProvider` (all M4.1).
- **`TrackerAdapter`** — provider-agnostic tracker sync (M2+).

## Key constraints

- **AI provider**: Default to VS Code LM API. BYOK and local are fallbacks. Class D (consumer OAuth token reuse) is permanently prohibited — Anthropic blocked Jan 2026, Google Feb 2026.
- **Model routing**: `config.yaml` routing entries are a model ID string or `"auto"`. Always use `resolveProviderFromConfig(task, root)` — never the old `getProvider()` helper which ignores config.
- **Model label**: every generation run must show `<model-id> (<provider>)` in the progress notification and the Generation Review panel header.
- **Token usage**: log to Saga Output Channel and show in review panel header after every call. Label VS Code LM estimates `(est.)`. BYOK adapters (M4.1+) return exact counts from provider SDKs.
- **Cancellation**: all generation `withProgress` must be `cancellable: true`. Convert `CancellationToken` → `AbortController` → `AbortSignal`; thread through `GenerationService` into `provider.generate()`. `onRegenerate` also receives the signal. Catch abort cleanly — info message, no error.
- **Secrets**: `context.secrets` (SecretStorage) for every credential. Zero secrets in `.saga/` or committed files.
- **LLM output**: always parse with Zod; never raw `JSON.parse`. Retry on parse failure with stricter prompt.
- **Webview `acquireVsCodeApi()`**: call exactly once — in `webview-ui/src/vscode-api.ts`. All bridges import from there.
- **Deletion**: all file deletions use `{ useTrash: true }` — recoverable from OS trash.
- **Tracker push**: always use `buildTrackerAdapter(root, secrets)` — never instantiate `JiraAdapter` / `AdoAdapter` directly in commands. Story push requires parent epic to be pushed first (F15b). Story points field is omitted by default; configure `jira.story_points_field_id` to enable. Jira ADF `content` must never be empty (toAdf pads with a space paragraph).
- **Tracker delete**: all deletes go through `trackerAwareDelete()` when item has `remote.key`. Remote delete failures must not hard-block local delete — always offer "Delete locally anyway?".
- **Sync safety**: sync is always explicit (user-triggered), previews before applying, idempotent. No background auto-push.
- **Pull correctness (revised — see the "sync always shows pull" fix below)**: when writing a pulled story, always run `StorySchema.parse()` on the merged object first. Store `local_hash` as `hashComparableStory(parsed)`. Store `remote.last_synced_hash` and the sync-store mapping's `last_synced_hash` as `hashRemoteStory(remote, ...)` computed directly from the fetched `RemoteStory` — **not** a hash of the parsed/merged object, even though that object is what gets written to disk. `parsed` may contain local-fallback values wherever the tracker's round-tripped text parsed empty (`remote.x || local.x`), but `hashRemoteStory()` never applies that fallback — hashing `parsed` for the baseline was the root cause of every sync showing a false "remote changed" forever, since the *next* fetch's `hashRemoteStory()` would never re-derive to the fallback value. Same pattern for epics: `local_hash: hashEpic(parsed)`, but `remote.last_synced_hash: hashRemoteEpic(remote, ...)`. It's correct and expected for `local_hash` to occasionally differ from `remote.last_synced_hash` right after a pull that used a fallback — that's genuine one-off drift the user should see, not a bug.
- **Story Editor passthrough**: `StoryMsg` (extension) and `StoryData` (webview) must always carry `remote` and `local_hash` through the postMessage round-trip. These fields are never edited by the UI — they are opaque sync state. Dropping them on save loses the remote key (causing re-create on next push) and breaks drift detection.
- **Epic Editor passthrough**: `EpicMsg` (extension) and `EpicData` (webview) must always carry `remote` and `local_hash` through the postMessage round-trip, exactly like the Story Editor. `EpicPanel`'s save handler must never reconstruct the `Epic` object via a fresh literal that omits these fields — write `{ ...existingEpic, ...editedFields }`, not a field-by-field rebuild. This is why epic editing has its own dedicated `EpicPanel` instead of reusing `GenerationReviewPanel`'s `draftToEpic()`, which does exactly this unsafe reconstruction (and additionally hardcodes `status: 'draft'`) — that's fine for its actual use case (reviewing brand-new, never-saved epics) but would corrupt sync state if pointed at an existing epic.
- **Epic edit story-impact check**: `saga.editEpic` must compare `title`/`description` (not `labels` — not fed into the story-generation prompt) against the on-disk values captured when the panel opened, not against some other cached copy, and must only offer to regenerate stories when the epic has 1+ existing stories. Never auto-regenerate — always require the explicit "Regenerate Stories" modal action, and never auto-delete existing stories on "Replace all existing stories" until the replacement stories are confirmed saved (same `onSaved`-gated pattern as `saga.splitStory` — see below).
- **Testing**: `@vscode/test-electron` for VS Code host integration tests; Vitest for pure logic (parsers, validators).
- **BYOK key pattern**: BYOK adapters (`AnthropicProvider`, `GeminiProvider`, `OpenAIByokProvider`) receive a `() => Promise<string | undefined>` key-getter callback at construction — never a raw key string, never a `SecretsManager` reference. This keeps the adapter testable and decoupled from the VS Code API.
- **Agent prompt — no presets in v1**: the prompt is generated without a target-agent preset; stack, directory layout, and story content are always included verbatim. Preset framing (Claude Code / Copilot / Gemini CLI / generic) is a P2 enhancement.
- **Agent prompt file path**: output is always `.saga/prompts/STORY-NNN.prompt.md`. The `writePrompt(sagaRoot, storyId, content)` helper in `saga-repo.ts` handles path construction. Never save to the workspace root. File is written only on explicit user Save — never eagerly on generation.
- **AGENTS.md lock**: `writeLock` stores a SHA-256 of the exact string written to `AGENTS.md`. On re-generation, if `AGENTS.md` exists but its current hash differs from the lock, the user must confirm before overwriting. If no lock file exists, treat `AGENTS.md` as potentially hand-written and always warn.
- **Workspace scanner**: never include `node_modules`, `.git`, `dist`, `build`, `out`, `.saga`, `.vscode` in any file listing. Respect a 200-file cap on candidate results to avoid freezing on large repos.
- **Agent prompt codebase context**: v1 uses heuristic scoring only — filename/path string overlap with story title + labels, no embeddings. Score 0–1; include files with score > 0.1, capped at top 20. Embeddings are P2.
- **Subtask ID generation**: subtask IDs are `SUB-NNN` scoped within a story (not globally unique). When creating new subtasks, find the max existing `id` within the story's `subtasks[]` array and increment.
- **Subtask hash inclusion (revised)**: `hashStory()` (subtasks included) is a purely-local, informational hash — it is **not** used anywhere in the tracker push/pull/sync path anymore (see the fix below for why). `local_hash`/`remote.last_synced_hash`/sync-store `last_synced_hash` for stories always use `hashComparableStory()` (no `subtasks`), matching `hashRemoteStory()`'s field set exactly. Subtask-level drift (did an already-pushed subtask change since its own last sync?) is checked separately, per-subtask, via `hashComparableSubtask(sub) !== sub.remote.last_synced_hash` — see `storyEffectiveStatus()` in `src/tree/saga-tree.ts`.
- **OpenRouter key pattern**: `OpenRouterProvider` uses the same `() => Promise<string | undefined>` key-getter callback as all other BYOK adapters. Key stored in SecretStorage under key name `saga.openrouter.apiKey`. Always send `HTTP-Referer: vscode-saga` and `X-Title: Saga` headers.
- **Template override resolution**: `loadTemplateSource(name, extensionUri, sagaRoot?)` checks `.saga/templates/<name>.hbs` first; falls back to the bundled default at `dist/generation/templates/<name>.hbs` (built from `src/generation/templates/<name>.hbs` by `copyTemplatesPlugin`). If `sagaRoot` is undefined (no workspace), always use the bundled default. Never read `src/generation/templates/` directly at runtime — only the `dist/` copy exists once packaged.
- **Export bundle size**: `docx` and `exceljs` are loaded via dynamic `import()` inside the export command handler to avoid adding ~2 MB to the extension's synchronous activation path.
- **Export module `vscode` isolation**: keep `src/export/format-helpers.ts` free of any `vscode` import. Only `src/export/collect.ts` (`collectBacklog()`) may import `vscode` — it's excluded from the Vitest suite (needs the VS Code test harness). If a renderer (`export-*.ts`) needs a new shared helper, add it to `format-helpers.ts`, not `collect.ts`, or its unit tests will fail to resolve `vscode` transitively.
- **PDF export intentionally omitted**: no lightweight pure-JS HTML→PDF renderer exists without either bundling a headless browser or producing plain hand-drawn layouts. Markdown export + print-to-PDF from any editor/browser covers the need. Revisit only if there's a concrete request and a viable dependency.
- **Story split — original deletion is save-gated**: `saga.splitStory` must never delete the original story before the replacement stories are confirmed saved. Use `GenerationReviewOptions.onSaved` (fired only after `writeStory`/`writeEpic` succeed) — never delete eagerly before opening the review panel, or a cancelled/closed panel loses the story with nothing to show for it.
- **Telemetry is local-only**: `TelemetryReporter` never makes a network call. Do not add one without an explicit product decision — shipping silent/fake telemetry (a checkbox that looks like it does something external but doesn't) is worse than no telemetry at all. If a real backend is added later, keep the `track({ command, provider?, storyCount? })` call sites unchanged and swap the sink inside `telemetry.ts`.
- **Getting Started state is always live, never a dismissed flag**: `GettingStartedPanel` recomputes `hasProvider`/`hasContext`/`hasEpic` from disk on every load and on `onDidChangeViewState` — it does not persist "user saw this" anywhere. Re-running `saga.gettingStarted` must always reflect current reality, not a stale one-time snapshot.
- **Subtask tracker push**: subtasks should be pushed only when the parent story has a `remote.key`. Subtask push is not included in `saga.pushAll` v1 — only explicitly via a dedicated "push subtasks" notification action, shown after both `saga.pushStory`'s own success notification and (post-M5.6-fixes) `saga.pushEpic`'s "Push N Stories" bulk follow-up, or via a resolution in Sync Review. Any new bulk-push flow that pushes stories on the user's behalf should offer the same "Push N Subtasks" follow-up rather than silently skipping subtasks — `pushOneStory()` itself never pushes them.
- **Subtask sync hash**: never use `hashSubtask()` (which includes `type`) when comparing against remote state — trackers don't model Saga's task/test/chore type. Always use `hashComparableSubtask()` / `hashRemoteSubtask()` for anything that touches `RemoteSubtask` or `last_synced_hash` on a pushed subtask.
- **Context file open**: `saga.openContextFile` must handle the case where the original registered path no longer exists (file moved/deleted); fall back to opening the `.saga/context/<filename>` copy if present, or show an info message if neither exists.
